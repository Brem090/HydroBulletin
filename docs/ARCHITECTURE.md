# Архітектура HydroBulletin після тижня 2

## Робочий конвеєр

```text
OnlineDataSource ─┐
                  ├─→ raw-архів → decode_codes → HydroObservation
LocalFileSource ──┘                                  ↓
                                      observation_measurements
                                                     ↓
                                  imports + observations (SQLite)
                                                     ↓
                                          консольний результат
```

Онлайн- і локальний режими відрізняються лише способом отримання початкового тексту. Декодер, raw-архівування та SQLite не містять мережевої логіки.

## Відповідальність модулів

- `models.py` — `Station`, агрегований запис `HydroObservation` і нормалізоване значення `HydroMeasurement`.
- `stations.py` — довідник 31 поста Львівської області, сформований на тижні 1.
- `sources.py` — `LocalFileSource`, `OnlineDataSource`, конфігурація `.env`, HTML/KOI8-U та базова перевірка відповіді.
- `decoder.py` — групи 0, 1, 2, 3, 4 і 8, `NIL`, часові мітки та відбір записів потрібної дати.
- `archive.py` — raw-файли, схема SQLite v2, журнал імпортів, SHA-256 і дедуплікація.
- `pipeline.py` — один керований сценарій `source → raw → decode → SQLite`.
- `main.py` — консольний інтерфейс локального або онлайн-режиму.

## Часова модель

З групи `YYGGn` формується локальна часова мітка ранкового спостереження. Група 3 отримує окрему мітку 20:00 попередньої доби. Тому обидва рівні зберігаються як значення одного параметра `WATER_LEVEL`, але в різні моменти часу. Це безпосередньо готує дані для графіка рівнів.

## Модель SQLite

### `imports`

Один рядок відповідає одному унікальному отриманому або локально імпортованому файлу. Основні поля: джерело, тип ZRUR, дата бюлетеня, шлях до raw-файла, SHA-256 та час імпорту.

### `observations`

Один рядок відповідає одному параметру одного поста в один момент часу:

```text
station_index + observed_at + parameter_code + value + unit
              + quality_status + source_type + source_file + import_id
```

Унікальність `station_index + observed_at + parameter_code` забезпечує базовий захист від повторного спостереження. Якщо правила декодування уточнено, повторна обробка того самого raw-файла використовує наявний `import_id` і додає лише параметри, яких ще немає. Повна робота з конфліктними версіями та ручними виправленнями належить до наступних етапів.

## Походження рішення

- Концепція «станція / параметр / час / значення / якість» адаптована з WaterML 2.0 без заяви про повну сумісність зі стандартом.
- Raw і структуроване сховище розділені відповідно до принципів керування екологічними часовими рядами (Bumberger et al. (2025) — Digital ecosystem for FAIR time series data management in environmental system science).
- Ланцюг `raw → imports → observations → майбутні продукти` реалізує мінімальний database-driven pipeline (Bumberger et al. (2025) — Digital ecosystem for FAIR time series data management in environmental system science) без зайвої серверної архітектури.
- Автоматизовані перевірки виконано стандартним `unittest`.
