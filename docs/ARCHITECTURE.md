# Архітектура HydroBulletin після тижня 3

## Наскрізний сценарій

```text
OnlineDataSource ─┐
LocalFileSource ──┼─→ FallbackDataSource → raw-архів → decoder ─┐
ArchiveDataSource ┘                                             │
                                                               ├→ SQLite
OnlineMeteoDataSource ─┐                                       │
Local/Archive SYNOP ───┴─→ meteorology → добові опади ─────────┘
                                                                  ↓
                                                     контроль якості
                                                                  ↓
                                             генератор бюлетенів
                                                                  ↓
                                      3 DOCX + походження даних
```

`workflow.py` координує послідовність операцій. Командний і графічний
інтерфейси формують `WorkflowRequest`, а правила декодування та створення
бюлетенів залишаються у відповідних модулях.

## Відповідальність модулів

- `models.py` — агрегований запис поста й нормалізоване вимірювання.
- `stations.py` — 71 унікальний гідропост трьох територій і 10 потрібних
  метеостанцій.
- `regions.py` — регіони, списки постів, шаблони й правила іменування DOCX.
- `sources.py` — локальне, онлайн- та архівне джерела, повторні спроби й
  тайм-аути.
- `decoder.py` — гідрологічні групи 0, 1, 2, 3, 4, 8 та `NIL`.
- `meteorology.py` — SM/SI, група `6RRRt`, UTC ↔ локальний час і сума 09–09.
- `batch.py` — пошук та хронологічний імпорт підтримуваних TXT.
- `archive.py` — raw, SQLite v3, усунення дублікатів, запити та походження
  даних продуктів.
- `quality.py` — консервативні автоматичні прапорці без зміни значень.
- `bulletins.py` — один параметризований генератор трьох Word-бюлетенів,
  включно з обходом вкладених таблиць офіційних шаблонів.
- `workflow.py` — один робочий сценарій імпорту, QC і генерації.
- `gui.py` — графічна форма запуску з DPI-масштабуванням у Windows.
- `main.py` — CLI, пакетний запуск і запуск GUI.

## Модель SQLite

### `stations`

Єдиний довідник гідрологічних постів і потрібних метеостанцій.

### `imports`

Один рядок відповідає одній спробі імпорту унікального джерела. `source_key`
обчислюється з типу джерела, типу повідомлення, дати та SHA-256 вмісту.
Однаковий текст в іншу дату не вважається тим самим імпортом.

### `observations`

Один параметр одного поста в один момент часу:

```text
station_index + observed_at + parameter_code + value + unit
              + quality_status + quality_message
              + source_type + source_file + raw_record + import_id
```

Унікальність `station_index + observed_at + parameter_code` не дозволяє
дублювати часовий ряд. Повторний імпорт може додати лише раніше відсутній
параметр.

### `products` і `product_observations`

`products` реєструє Word-бюлетень, регіон, дату, вихідний шлях і метадані.
Зв’язувальна таблиця фіксує кожне використане вимірювання. Звідси
відновлюється повний шлях:

```text
DOCX → product → observation → import → raw_path + source_hash
```

## Контроль якості

Правила не виправляють початкові значення. Вони лише зберігають прапорець і
пояснення:

- `VALID` — значення пройшло початкові правила;
- `MISSING` — значення або обов’язкове поле відсутнє;
- `SUSPICIOUS` —  потрібна увага;
- `OUT_OF_RANGE` — значення поза консервативним фізичним інтервалом;
- `INCONSISTENT_CHANGE` — кодована зміна не дорівнює різниці рівнів за дві
  послідовні доби.

Від’ємні рівні води допустимі: знак сам по собі не є помилкою.

## SYNOP та мапінг опадів

Метеорологічні записи зберігаються у тій самій таблиці `observations` з
параметром `PRECIPITATION`. Мапінг лежить у
`config/precipitation_mapping.json`, тому відповідність можна змінювати без
редагування Python-коду. Для оперативного значення пов’язана метеостанція має
пріоритет над гідрологічною групою опадів; використане джерело зберігається у
даних про сформований продукт.

## Оновлення попередніх даних

Схема v2 оновлюється до v3 автоматично. Ідентифікатори імпортів і
спостережень при цьому зберігаються. Карта, графіки, Excel-звіти, водність і
льодові явища до поточного етапу не входять.
